# 流程说明 —— CarrorOS Delivery 怎么做的

> 这份文档回答三个问题：**它怎么运转？我该在哪一步做什么？产物从哪来？**
> 全部命令都可直接复制执行（在装了本产品的项目根目录下）。

---

## 0. 一句话

```
你写目标 → AI 问清一次 → 无人值守执行 → 交付代码 + 一份给客户的报告
```

四段里只有第一段需要你在场。第二段只问「一次」（一张卡一个问题，能自答的不问你），
第三段你不必在场，第四段你回来验收。

---

## 1. 全景时序

```
┌────────────┐   ① 起目标    ┌──────────────────────────────────────┐
│  你        │ ────────────► │ Phase 0：澄清（唯一需要你的阶段）      │
│            │               │  · 先探索代码/文档，能自答的不问       │
│            │ ◄──────────── │  · 一次只问一个问题，直到没有决策项    │
│            │   ② 回答      │  · 自判 L1/L2（你不用记参数）          │
└────────────┘               │  · 产出 research.md → plan.md         │
                             └───────────────┬──────────────────────┘
                                             │ ③ plan-done（过 ResearchGate + PlanGate）
                                             ▼
                             ┌──────────────────────────────────────┐
                             │ Phase 1→N：执行（你可以离开）          │
                             │  每个 step：动手前先更新文档+写证据    │
                             │  · 门禁在每次工具调用前拦截            │
                             │  · L2 进 worktree 隔离，改不到主工作区 │
                             │  · 卡点按决策链自决；硬边界只记录       │
                             └───────────────┬──────────────────────┘
                                             │ ④ 全部 step 完成 → verify
                                             ▼
                             ┌──────────────────────────────────────┐
                             │ 退出报告（你回来只看这个）             │
│            │ ◄──────────── │  · 内部版：真相源（含 verdict/证据）   │
│  你        │   ⑤ 验收      │  · 客户版：七节，可直接发给付费方      │
└────────────┘               └──────────────────────────────────────┘
```

## 2. 五套系统各管什么

| # | 系统 | 什么时候被调用 | 管什么 | 落在哪 |
|---|------|---------------|--------|--------|
| ① | **lx-goal** | 你说 `/lx-goal <目标>` | 决定「什么时候调哪个生命周期命令」；只做指令层，不自己管状态 | `.claude/skills/lx-goal/` |
| ② | **文档系统** | 每次生命周期命令 | 建/写任务文档：research.md、plan.md、executor.md、handoff.md | `.omc/tasks/{日期}/{任务}/` |
| ③ | **令牌系统** | 每次状态变更 | 唯一状态源（CAS 写 + 文件锁），防并发写坏 | `.omc/tokens/{日期}/{任务}.json` |
| ④ | **抗 compact** | 会话开始 / 压缩前 / 续跑 | 状态全在磁盘，对话丢了也能从 handoff 续上 | `.omc/session-handoff.md` + token |
| ⑤ | **hooks 门禁** | 每次工具调用前/后 | 14 道门拦截 + fail-closed + 写审计 | `.omc/audit/{日期}.jsonl` |

**关键设计**：①只是指令层，②③④⑤是引擎。换成别的 CLI 或别的技能，引擎不动、状态格式不变。

## 3. 生命周期命令表（真实命令）

所有命令都可加 `--task-dir <任务目录>` 精确定位；不给则用当前活动任务。

| 阶段 | 命令 | 会发生什么 |
|---|---|---|
| 起目标 | `lx-goal.py on "<目标>" --level L1\|L2` | 建任务目录 + token，状态 `CLARIFY` |
| 澄清完成 | `lx-goal.py phase0-done` | research.md 写完 → `PLANNING` |
| 计划通过 | `lx-goal.py plan-done` | 过 ResearchGate + PlanGate → `EXECUTING`（L2 在此起 worktree） |
| 每步完成 | `lx-goal.py tick` | 校验该步证据块存在 → 推进 step |
| 跑验证 | `carros_base.py verify` | 回归 TDD，输出 `VERIFIED` 才算这步过 |
| 出报告 | `lx-goal.py report` | 内部版 `state/goal-report.md`（含 verdict） |
| 出客户报告 | `lx-goal.py report --format client --out 交付报告.md` | 客户版七节 |
| 验收 | `lx-goal.py accept` | 双法官验收（可选，高风险任务建议跑） |
| 收尾 | `lx-goal.py done` | 归档 + 清理（L2 收尾强制跑后置 TDD） |
| 查状态 | `lx-goal.py status --task-dir <任务目录>` | 阶段 / 完成数 / 风险 / token / lock |
| 续跑 | `carros_base.py resume <任务目录>` | 换会话后从断点接上 |

## 4. 一次真实任务，产物长什么样

```
.omc/
├── tasks/20261027/把官网首页改成响应式-4be89f5b/
│   ├── research.md            # 背景/约束/不确定性/依赖树/方案（8 节）
│   ├── plan.md                # 步骤 + 验收条件 + L2 的 TDD 判据
│   ├── executor.md            # 每步证据块（EV-<step>：改了啥/断言啥/exit_code）
│   ├── handoff.md             # 断点导航（换会话靠它续上）
│   ├── working-set.yaml       # 本次允许触碰的路径契约
│   ├── evidence.jsonl         # 证据流水
│   └── state/goal-report.md   # 内部版退出报告（含 **status**/**confidence**）
├── tokens/20261027/把官网首页改成响应式-4be89f5b.json   # 唯一状态源
├── audit/2026-10-27.jsonl     # 门禁判定流水（每次拦截/审批都在这）
└── session-handoff.md         # 会话级恢复指针
```

**你要看的就是两份**：`state/goal-report.md`（真相）、`交付报告.md`（给客户）。

## 5. 交付报告从哪来

| | 内部版 | 客户版 |
|---|---|---|
| 生成命令 | `report` | `report --format client --out X.md` |
| 读者 | 你 / AI / 审计 | 付费方 |
| 术语 | EV 块、uncertified、GateKeeper、verdict status/confidence | 无（硬约束：出现即测试失败） |
| 交付项 | step 编号（S1/S2） | plan.md 里的人类可读标题 |
| 特有内容 | 未认证项代码、gatekeeper 摘要 | **"需要你决定的事"表格**（事项/为什么需要你定/我的建议+依据） |

客户版七节：结论 · 本次交付内容 · 这些内容是怎么验证的 · **需要你决定的事** · 本次未做的部分 · 需管理员权限执行的操作 · 验收方式。

第四节的生成逻辑：把三类真实信号汇总成一张表——
硬边界拦截（你才能执行的操作）、推迟决策（AI 判断需要业务输入的事）、
中高风险跳过（本次未纳入、建议后续处理）。**纯自主 agent 给不出这个，因为它不承认自己不确定。**

## 6. 为什么换会话不失忆（抗 compact）

| 层 | 文件 | 作用 |
|---|---|---|
| 会话级 | `.omc/session-handoff.md` | 压缩/重启后第一步读它 |
| 任务级 | `{任务}/handoff.md` + `token.json` | 当前阶段、下一个 step、已验证证据 |
| 计划级 | `plan.md` | 冻结的计划（AI 不得私自改范围） |
| 证据级 | `executor.md` + `evidence.jsonl` | 已做过什么、凭什么算完成 |

恢复动作只有一条命令：

```bash
python3 .claude/scripts/carros_base.py resume .omc/tasks/20261027/<任务目录>
```

**设计前提**：对话是易失的，磁盘是可信的。凡是「AI 必须记住」的东西，一律落盘。

## 7. 门禁在哪一层生效

```
AI 想调用工具（写文件 / 跑命令 / 读敏感路径）
        │
        ▼
hook-launcher.py ──► pretool-gate.py ──► 14 道门依次判定
                                            │
              ┌─────────────────────────────┼──────────────────────────┐
              ▼                             ▼                          ▼
           ALLOW                        ASK_USER                    拦截
        （正常执行）              （等你点头，默认不放行）      （拒绝 + 写审计）
```

- **fail-closed**：安全门自身崩了 → 判定为拒绝，而不是静默放行。
- **审计**：每次判定写 `.omc/audit/{日期}.jsonl`，事后可归因。
- **诚实说明**：默认交互模式必须你点头；若开启自动放行，敏感门退化为「拦截 + 留痕」，报告里可查。

---

## 8. 它不做什么

- 不判断业务对不对（管行为，不管判断）
- 不保证零事故（减少翻车 + 留可审计记录）
- 不提升模型智商（只让模型更守规矩）
- 不支持 Windows 原生（依赖 `fcntl` 文件锁；WSL 可用）
