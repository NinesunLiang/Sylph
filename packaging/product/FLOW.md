# 流程说明 —— CarrorOS Delivery 怎么做的

> 这份文档回答三个问题：**它怎么运转？我该在哪一步做什么？产物从哪来？**
> 全部命令都可直接复制执行（在装了本产品的项目根目录下）。

---

## 0. 一句话

```
你写目标 → AI 问清一次 → 无人值守执行 → 交付代码 + 一份给客户的报告
```

四段里只有第一段需要你在场。第二段只问「一次」（一张卡一个问题，能自答的不问你），
第三段你不必在场，第四段你回来验收。

---

## 1. 全景时序

```
┌────────────┐   ① 起目标    ┌──────────────────────────────────────┐
│  你        │ ────────────► │ Phase 0：澄清（唯一需要你的阶段）      │
│            │               │  · 先探索代码/文档，能自答的不问       │
│            │ ◄──────────── │  · 一次只问一个问题，直到没有决策项    │
│            │   ② 回答      │  · 自判 L1/L2（你不用记参数）          │
└────────────┘               │  · 产出 research.md → plan.md         │
                             └───────────────┬──────────────────────┘
                                             │ ③ plan-done（过 ResearchGate + PlanGate）
                                             │    L2 在此建立 worktree 隔离（§5）
                                             ▼
                             ┌──────────────────────────────────────┐
                             │ Phase 1→N：执行（你可以离开）          │
                             │  每个 step：动手前先更新文档+写证据    │
                             │  · 门禁在每次工具调用前拦截            │
                             │  · L2 的代码写入被限制在 worktree 内   │
                             │    （写主树会被 worktree-scope 拦下）  │
                             │  · 卡点按决策链自决；硬边界只记录       │
                             └───────────────┬──────────────────────┘
                                             │ ④ 全部 step 完成 → verify
                                             ▼
                             ┌──────────────────────────────────────┐
                             │ 退出报告（你回来只看这个）             │
│            │ ◄──────────── │  · 内部版：真相源（含 verdict/证据）   │
│  你        │   ⑤ 验收      │  · 客户版：七节，可直接发给付费方      │
└────────────┘               │  · 归档时 worktree 合回发起分支        │
                             └──────────────────────────────────────┘
```

## 2. 五套系统各管什么

| # | 系统 | 什么时候被调用 | 管什么 | 落在哪 |
|---|------|---------------|--------|--------|
| ① | **lx-goal** | 你说 `/lx-goal <目标>` | 决定「什么时候调哪个生命周期命令」；只做指令层，不自己管状态。**L2 另加 worktree 隔离（§5）** | `.claude/skills/lx-goal/` |
| ② | **文档系统** | 每次生命周期命令 | 建/写任务文档：research.md、plan.md、executor.md、handoff.md | `.omc/tasks/{日期}/{任务}/`（§4） |
| ③ | **令牌系统** | 每次状态变更 | 唯一状态源（CAS 写 + 文件锁），防并发写坏 | `.omc/tokens/{日期}/{任务}.json` |
| ④ | **抗 compact** | 会话开始 / 压缩前 / 续跑 | 状态全在磁盘，对话丢了也能从 handoff 续上 | `.omc/session-handoff.md` + token |
| ⑤ | **hooks 门禁** | 每次工具调用前/后 | 14 道门拦截（含 `worktree-scope` 隔离门）+ fail-closed + 写审计 | `.omc/audit/{日期}.jsonl` |

**关键设计**：①只是指令层，②③④⑤是引擎。换成别的 CLI 或别的技能，引擎不动、状态格式不变。

## 3. 生命周期命令表（真实命令）

所有命令都可加 `--task-dir <任务目录>` 精确定位；不给则用当前活动任务。

| 阶段 | 命令 | 会发生什么 |
|---|---|---|
| 起目标 | `lx-goal.py on "<目标>" --level L1\|L2` | 建任务目录 + token，状态 `CLARIFY` |
| 澄清完成 | `lx-goal.py phase0-done` | research.md 写完 → `PLANNING` |
| 计划通过 | `lx-goal.py plan-done` | 过 ResearchGate + PlanGate → `EXECUTING`（**L2 在此建 worktree，§5**） |
| 每步完成 | `lx-goal.py tick` | 校验该步证据块存在 → 推进 step |
| 跑验证 | `carros_base.py verify` | 回归 TDD，输出 `VERIFIED` 才算这步过 |
| 出报告 | `lx-goal.py report` | 内部版 `state/goal-report.md`（含 verdict） |
| 出客户报告 | `lx-goal.py report --format client --out 交付报告.md` | 客户版七节 |
| 验收 | `lx-goal.py accept` | 双法官验收（可选，高风险任务建议跑） |
| 收尾 | `lx-goal.py done` | 归档 + **worktree 合回发起分支** + 清理（L2 强制跑后置 TDD） |
| 查状态 | `lx-goal.py status --task-dir <任务目录>` | 阶段 / 完成数 / 风险 / token / lock |
| 续跑 | `carros_base.py resume <任务目录>` | 换会话后从断点接上 |

## 4. 任务地址系统：`.omc/tasks/{日期}/{任务名}` —— 为什么这是核心

**一句话：任务地址是稳定的、可校验的、可寻址的字符串，不是"某个目录里的一堆文件"。**

### 4.1 唯一合法形态

```
.omc/tasks/YYYYMMDD/{task_name}          ← 任务文档目录（唯一合法形态）
.omc/tokens/YYYYMMDD/{task_name}.json    ← 同名令牌（路径同构，一一对应）
```

两者**同名、同日**，由同一条路径推导出来。给定任意一方都能算出另一方：

```python
# .claude/scripts/lx-goal.py::_token_path_for_plan
task_dir = .omc/tasks/20261027/把官网首页改成响应式-4be89f5b
token    = .omc/tokens/20261027/把官网首页改成响应式-4be89f5b.json
```

### 4.2 三种可接受的输入（都指向同一个地址）

| 你给的形式 | 例子 | 用途 |
|---|---|---|
| 绝对路径 | `/Users/me/proj/.omc/tasks/20261027/demo` | 脚本内部、跨目录调用 |
| 相对仓库根 | `.omc/tasks/20261027/demo` | 命令行日常 |
| 相对 tasks 根 | `20261027/demo` | 简短输入 |

解析器 `resolve_task_document()` 负责把三者归一，**不接受第四种猜测**：

- 拒绝 `..` 路径逃逸、拒绝绝对路径逃逸出 tasks 根
- 拒绝非法日期、拒绝非法任务名
- 失败就**明确报错**（fail-explicit），不猜、不模糊匹配

### 4.3 任务名校验规则（为什么不能随便起名）

```
允许：中文 / 英文字母 / 数字 / . _ -
要求：首字符必须是字母、数字或中文（不能以 . - _ 开头）
上限：≤ 200 字符
拒绝：路径分隔符 / .. / 绝对路径
```

**为什么**：任务名会直接变成目录名、令牌文件名、分支名的一部分。允许 `../` 就等于允许
写穿到仓库外；允许 `/` 就等于允许一个任务散落在不同目录。这条校验是**路径注入的第一道防线**。

### 4.4 为什么"稳定"——四个消费方都依赖同一个地址

| 消费方 | 用地址做什么 | 地址变了会怎样 |
|---|---|---|
| **令牌系统** | 用任务目录反推 token 路径（`tokens/{date}/{name}.json`） | 状态读不到 → 任务失联 |
| **跨会话恢复** | `resume <任务目录>` 写活跃指针，后续 `tick`/`verify` 免 `--task-dir` | 换会话接不上活 |
| **审计** | 证据/门禁记录按任务归集 | 事后无法归因"哪次改是为了哪个任务" |
| **归档** | `mv` 到 `archive/{日期}_{slug}/{slug}`，并在**原地址留符号链接** | 老命令/书签/脚本全部 404 |

归档那段值得单独说（`carros_base.py` archive 步骤）：

```
归档前： .omc/tasks/20261027/demo/            ← 真实目录
归档后： .omc/archive/20261027_demo/demo/     ← 真实内容搬这里
        .omc/tasks/20261027/demo → 符号链接  ← 原地址仍然可用
```

**地址不变，内容搬家。** 所以任何指向老任务的命令、链接、审计记录都还能解析——
这就是"稳定系统"的实际含义。

### 4.5 活跃指针：给"最近一个任务"一个确定名字

```json
// .omc/state/active-resume.json
{ "date": "20261027", "slug": "demo",
  "task_dir": ".../tasks/20261027/demo",
  "token_path": ".../tokens/20261027/demo.json",
  "activated_at": "2026-10-27T..." }
```

存在意义：`tick` / `verify` / `report` 不带 `--task-dir` 时，**只认这个指针**，
不扫描、不猜"哪个任务最近改过"。扫描猜测会在多任务并行时把状态写到错的账本上。

同时它也做冲突保护：想切到另一个任务时，若当前任务未归档，会拒绝覆盖并提示先归档
或显式指定 `--task-dir`——避免跨任务污染。

## 5. worktree 隔离执行：`安全` 这一条的技术底座

**一句话：L2（完备模式）任务的代码改动发生在独立的 git worktree 里，写主树会被门禁拦下。**

### 5.1 为什么需要它

无人值守时，AI 可能同时有多条线在动（子任务、后台修复、你手头的另一个终端）。
若都在主树工作区改代码：**多进程互相踩**，一个任务的半成品会污染另一个任务的验证结论，
"隔离"就形同虚设。

### 5.2 什么时候建立

| 级别 | 行为 |
|---|---|
| **L1 简易** | 不建隔离（`enter_isolation_if_complete` 直接 no-op）——单模块小改，收益低于成本 |
| **L2 完备** | **一定建**：`plan-done` 通过 ResearchGate + PlanGate 后、进入执行态时创建 |

人类裁决原话（代码注释里保留）：「完备模式**一定**在 worktree 下」。

### 5.3 建在哪、怎么建

```bash
# .claude/scripts/worktree_utils.py
git worktree add .omc/worktrees/task-isolated-{task_id}-{hash8} -b task-isolated-{task_id}-{hash8}
```

- 位置：`.omc/worktrees/task-isolated-<任务id>-<随机8位>`
- 分支：同名，独立于你的 `main`
- token 里落两个字段：`worktree`（绝对路径）+ `worktree_branch`（分支名）

### 5.4 关键设计：`.omc` 反向链接回主树（隔离代码，共享账本）

`git worktree add` **不会复制被 gitignore 的 `.omc/`**——实测 worktree 里只有 `.claude/`。
而任务文档、令牌、审计全在 `.omc/`。

所以创建后会做一次链接：

```
.omc/worktrees/task-isolated-xxx/.omc  →  (主树) .omc
```

**为什么不把账本也隔离**：worktree 收尾时会被 `git worktree remove` 删掉。
账本若在里面，证据、审计、token 会**随 worktree 一起永久消失**。
链接回主树后：代码在沙箱里改，账本始终在主树 —— 隔离作用域只有"代码"。

> 平台不支持符号链接时（少数 Windows 环境），`_link_ledger` 返回 False，
> 调用方退化为主树绝对路径 + `--task-dir`，而不是假装隔离成功。

### 5.5 门禁强制：不靠自觉，靠 `worktree-scope`

隔离执行期间，`worktree-scope` 门（第 13 道）会检查每次写操作的目标路径：

| 写哪里 | 判定 | 原因 |
|---|---|---|
| worktree 内路径 | ✅ 放行 | 这是应该工作的地方 |
| **主树代码路径** | ⛔ 拦下，并**指向 worktree 内等价路径** | 在 worktree 下干活由机制保证 |
| `.omc/`（任意） | ✅ 放行 | 账本按设计共享主树 |
| 仓库外路径 | ✅ 放行 | 不归本仓治理 |
| 非写操作（读/搜索） | ✅ 放行 | 只读无冲突 |
| 无活跃隔离（无 token 或无 `worktree` 字段） | no-op | L1 与普通开发不受影响 |

**要点**：这道门不是"提醒"，是**拦截**；且它给的是可执行的替代路径，不是一句"不允许"。

### 5.6 怎么收尾

```
done → 后置 TDD 全绿 → merge_worktree（把 worktree 分支合回发起分支）
     → git worktree remove → 主树恢复干净
```

- L2 收尾**强制**跑后置 TDD；worktree 未合回不得归档
- 残留清理：`worktree_utils.gc()` 扫 `.omc/worktrees/`，按分支年龄/归档记录回收
- 归档后 token 里保留 `worktree_branch`，审计能追到"这批改动来自哪个隔离分支"

### 5.7 你能拿它证明什么

对客户可以说的是**可验证的**一句：

> 这次交付的代码改动全部发生在一个独立 git 分支（`task-isolated-*`）里，
> 执行期间写主工作区会被门禁拦下，最后合回主分支——过程有分支记录和审计可查。

这比"我很小心"强，因为**客户可以自己 `git branch -a` 看到那条隔离分支**。

## 6. 一次真实任务，产物长什么样

```
.omc/
├── tasks/20261027/把官网首页改成响应式-4be89f5b/     ← 稳定地址（§4）
│   ├── research.md            # 背景/约束/不确定性/依赖树/方案（8 节）
│   ├── plan.md                # 步骤 + 验收条件 + L2 的 TDD 判据
│   ├── executor.md            # 每步证据块（EV-<step>：改了啥/断言啥/exit_code）
│   ├── handoff.md             # 断点导航（换会话靠它续上）
│   ├── working-set.yaml       # 本次允许触碰的路径契约
│   ├── evidence.jsonl         # 证据流水
│   └── state/goal-report.md   # 内部版退出报告（含 **status**/**confidence**）
├── tokens/20261027/把官网首页改成响应式-4be89f5b.json   # 唯一状态源（同构路径）
├── worktrees/task-isolated-.../                      # L2 隔离工作区（代码在这里改）
├── audit/2026-10-27.jsonl     # 门禁判定流水（每次拦截/审批都在这）
├── state/active-resume.json   # 活跃任务指针（续跑唯一入口）
└── session-handoff.md         # 会话级恢复指针
```

**你要看的就是两份**：`state/goal-report.md`（真相）、`交付报告.md`（给客户）。

## 7. 交付报告从哪来

| | 内部版 | 客户版 |
|---|---|---|
| 生成命令 | `report` | `report --format client --out X.md` |
| 读者 | 你 / AI / 审计 | 付费方 |
| 术语 | EV 块、uncertified、GateKeeper、verdict status/confidence | 无（硬约束：出现即测试失败） |
| 交付项 | step 编号（S1/S2） | plan.md 里的人类可读标题 |
| 特有内容 | 未认证项代码、gatekeeper 摘要 | **"需要你决定的事"表格**（事项/为什么需要你定/我的建议+依据） |

客户版七节：结论 · 本次交付内容 · 这些内容是怎么验证的 · **需要你决定的事** · 本次未做的部分 · 需管理员权限执行的操作 · 验收方式。

第四节的生成逻辑：把三类真实信号汇总成一张表——
硬边界拦截（你才能执行的操作）、推迟决策（AI 判断需要业务输入的事）、
中高风险跳过（本次未纳入、建议后续处理）。**纯自主 agent 给不出这个，因为它不承认自己不确定。**

## 8. 为什么换会话不失忆（抗 compact）

| 层 | 文件 | 作用 |
|---|---|---|
| 会话级 | `.omc/session-handoff.md` | 压缩/重启后第一步读它 |
| 任务级 | `{任务}/handoff.md` + `token.json` | 当前阶段、下一个 step、已验证证据 |
| 计划级 | `plan.md` | 冻结的计划（AI 不得私自改范围） |
| 证据级 | `executor.md` + `evidence.jsonl` | 已做过什么、凭什么算完成 |
| 地址级 | `.omc/state/active-resume.json` | 「最近一个任务」有确定名字，不靠扫描猜测（§4.5） |

恢复动作只有一条命令：

```bash
python3 .claude/scripts/carros_base.py resume .omc/tasks/20261027/<任务目录>
```

**设计前提**：对话是易失的，磁盘是可信的。凡是「AI 必须记住」的东西，一律落盘。

## 9. 门禁在哪一层生效

```
AI 想调用工具（写文件 / 跑命令 / 读敏感路径）
        │
        ▼
hook-launcher.py ──► pretool-gate.py ──► 14 道门依次判定
                                            │
              ┌─────────────────────────────┼──────────────────────────┐
              ▼                             ▼                          ▼
           ALLOW                        ASK_USER                    拦截
        （正常执行）              （等你点头，默认不放行）      （拒绝 + 写审计）
```

- **worktree-scope**（第 13 道）：隔离执行期拦主树写入，见 §5.5
- **fail-closed**：安全门自身崩了 → 判定为拒绝，而不是静默放行
- **审计**：每次判定写 `.omc/audit/{日期}.jsonl`，事后可归因
- **诚实说明**：默认交互模式必须你点头；若开启自动放行，敏感门退化为「拦截 + 留痕」，报告里可查

## 10. 它不做什么

- 不判断业务对不对（管行为，不管判断）
- 不保证零事故（减少翻车 + 留可审计记录）
- 不提升模型智商（只让模型更守规矩）
- 不支持 Windows 原生（依赖 `fcntl` 文件锁；WSL 可用）
- **L1 任务不建 worktree 隔离**（单模块小改，收益低于成本；需要隔离就用 L2）
