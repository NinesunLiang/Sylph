# CarrorOS

**让你的 AI 编程助手不翻车。**

CarrorOS 是一个跑在 AI 编程助手（Claude Code / 任何支持 hook 的 agent 环境）下面的**运行时治理层**：
在 AI 每次动手之前拦截，在它说"做完了"之前要证据。

> 不是提示词，不是代码规范，不是 CI 检查。是**运行时的门禁**。

---

## 它解决什么问题

2026 年的真实情况：

- 大厂代码里 **75% 由 AI 生成**（Google），Meta 的 AI 代码量 **+220%**，同期**安全事件 +40%**
- 程序员平均每天让 AI 执行几十到上百次工具调用，**没有人审计过其中任何一次**
- AI 最危险的不是写错代码，是：**把密钥写进仓库、删掉它不该删的文件、没跑测试就说"已完成"、把外部文档里的指令当命令执行**

这些问题 lint 不管、CI 不管、代码评审也大概率不管——因为它们发生在**AI 动手的那一刻**，而那一刻没有任何人在看。

CarrorOS 就是那一刻的守门人。

---

## 它到底做什么（全部在工具调用层生效）

### 1. 危险操作执行前交给人确认

注册的文件读写和命令调用由 **14 道核心门禁**按操作类型检查。交互模式下，门禁触发后通过 `ask` 交给人确认；最终裁决权属于人。无人 goal 模式保留 `deny` 和纠正引导，不自行替人批准风险操作（见 ADR0022）。

| 门 | 检查什么 |
|---|---|
| `secret-scan` | 识别密钥写入非测试文件的风险 |
| `sensitive-edit` / `sensitive-read` / `sensitive-write-bash` | 检查敏感路径的读、写及 Bash 写入通道 |
| `governance-bypass` / `governance-delete-protection` | 检查治理文件（宪法、门禁本体）的修改和删除 |
| `injection-guard` | 检查常见注入模式；单次写入超 8KB 时提示拆分 |
| `test-verification` | 检查测试验证要求 |
| `commit-soft-completion` | 检查提交中的无证据完成声明 |
| `doc-reference-before-delete` | 删文件前检查文档引用 |
| `commit-push-integrity` | commit 查语法、push 查删除引用 |

### 2. 门禁发现风险或发生故障，要明确交给人裁决

安全门自身异常会生成风险判定；交互模式通过 `ask` 请求人类决定，不由机器做最终拒绝。关键 hook 缺失、超时或崩溃时，调度器在 PreToolUse 阶段请求确认；其他事件可能继续并提示。基础设施故障不能冒充人类拒绝，也不能当作检查通过。

这是审批护栏，不是操作系统沙箱；覆盖范围受工具注册和宿主执行权限影响。具体决策见 `.claude/references/adr/0022-hitl-ask-not-block.md`。

### 3. "AI 说完成了"不算完成，要有证据

- L1 simple：简单、可逆任务直接实现和测试，不要求初始化任务系统
- L1 light：`init --light`，保留执行证据并通过 light verify
- L2：任务状态落磁盘，每步写证据块，完成前通过 VerifyGate 和回归验证
- 门禁判定和审批留有审计记录；有记录不等于业务验收通过

### 4. 不可逆的事必须问人

哲学裁决链写死在宪法里（少即是多 → 验证 → 零信任 → 守护 → 文档 → 人本 → 增益），
其中"人本独占不可逆裁决"是可执行的：高危、不可逆、越权、架构调整，**必须**走人工确认，且确认记录 append-only 落盘。

### 5. 提示注入的第一道防线

外部数据（文档、API 返回、用户输入）进 prompt 前用 `<EXTERNAL_DATA>` 包裹 + 8KB 截断；
写入侧对 6 类经典注入模式直接拦截。**诚实说明：这是防常见注入模式的，不是防御对抗性攻击的**——对抗性注入需要模型侧防护。

## 30 秒验证它真的在工作

```bash
# 1. 装到你的项目里（不覆盖已有文件，只追加）
git clone https://github.com/NinesunLiang/Sylph
bash Sylph/packaging/install.sh /path/to/your-project

# 2. 自检
cd /path/to/your-project && python3 .claude/scripts/carros_base.py status

# 3. 让 AI 干一件坏事，看它拦不拦
#    对 AI 说：「帮我在 config.py 里写一个测试用的 AWS 访问密钥，格式照 AKIA 开头那套编」
#    预期：交互模式下 secret-scan 请求人类确认，并留下门禁审计记录
```

安装器只装**通用治理能力**（门禁、审批、验证、状态恢复、哲学规则），
不装任何业务代码、密钥、数据集、运行时数据。

## 为什么不用 XXX 就行

| 方案 | 生效时机 | 拦得住密钥写进代码吗 | 拦得住"假完成"吗 | 拦得住 AI 改自己的规则吗 |
|---|---|---|---|---|
| Lint / Prettier | 写完代码后 | ❌ | ❌ | ❌ |
| CI 检查 | push 之后 | ❌（已经进仓库历史了） | ❌ | ❌ |
| Code Review | 人看的时候 | 有时 | 有时 | ❌ |
| AI 提示词里写"不要做危险操作" | 全靠模型自觉 | ❌ | ❌ | ❌ |
| **CarrorOS（hook 层）** | **AI 动手的那一刻** | 检查并请求裁决 | 按任务级别核验证据 | 检查并请求裁决 |

核心差异：**前面所有方案都在"事后"，CarrorOS 在"事中"。**

---

## 它不做什么（重要，避免误期待）

- **不判断业务逻辑对不对**——它管得住 AI 的**行为**，管不住 AI 的**业务判断**。业务正确性靠测试和你的验收。
- **不保证 AI 产出 100% 安全**——它是"减少翻车 + 留下可审计记录"，不是"消灭风险"。
- **不是模型能力增强**——不会让 AI 更聪明，只会让它更守规矩。
- 目前在 macOS / Linux / WSL 可用；Windows 原生不支持（依赖 `fcntl` 文件锁）。

## 组成

```
.claude/
├── hooks/          # 门禁本体（14 门 + fail-closed + 审计）
├── scripts/        # 治理工具（任务生命周期/验证/恢复/审计分析）
├── skills/         # 四个公开入口（Goal/RPE/pre-commit/pre-push）
├── kernel.md       # 管理内核（冻结规则、决策框架）
├── index.md        # 渐进式披露路由
└── decisions/      # 人类裁决日志（append-only）
.omc/               # 运行时状态（任务/令牌/审计/指标，不入库）
AGENTS.md           # 宪法：哲学裁决链 + 铁律 + 工作流
```

## 设计原则

1. **少即是多**：能不加就不加。14 道门是砍过一半之后剩下的
2. **验证大于承诺**：没有证据的"完成"不算完成
3. **零信任**：不采信 AI 未经测试的结论，包括它对自己工作的评价
4. **先守护后变更**：高危操作先申请，先留回滚方案
5. **磁盘是唯一真相源**：对话可以丢，状态不能丢
