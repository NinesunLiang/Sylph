# 0002. Token + Lock 双层任务生命周期

**日期**: 2026-07-24
**来源**: task-architecture/orchestrator.md, 任务编排设计

## 上下文

AI 在执行长任务时需要跨会话跟踪任务的生命周期。会话可能因为超时、紧凑（compact）、手动停止或崩溃而中断。需要一个机制来：

1. 知道某个任务已启动但未完成
2. 防止同一任务被两个会话同时执行
3. 在紧凑事件后恢复任务状态
4. 不引入外部基础设施依赖

## 决策

实施两层架构：

**Token 层**（`.omc/token.json`）：
- 轻量 JSON 文件，存储任务元数据：`id`、`status`、`createdAt`、`updatedAt`、`sessionId`、`outline`
- 不可变生命周期：`pending → running → completed | failed | aborted`
- 紧凑事件后通过 token 恢复上下文

**Lock 层**（`.omc/lock`）：
- 纯锁文件，包含当前 PID 和启动时间戳
- 进程退出时自动释放（操作系统级清理）
- 进程启动时检查锁文件是否存在且持有者存活 → 存活着拒绝，否则清理旧锁

Token 不可变使得紧凑时只需要重放 token 状态链；Lock 文件确保并发安全。

## 替代方案

- **单文件状态** — 只用一个 JSON（如 `state.json`）存储所有状态。缺点是紧凑事件写入时可能产生脏读，并发环境下产生竞态条件，无法原子地变更部分状态。
- **数据库依赖** — 使用 SQLite 或 Redis 存储任务生命周期。优点是 ACID 保证；缺点是为一个 CLI 工具引入持久层太重，增加部署复杂度，违反 "zero external deps" 原则。
- **仅锁文件** — 只有 lock 没有 token。优点是简单；缺点是会话之间无法传递任务元数据，紧凑后完全丢失上下文。
- **Git branch 状态** — 通过 git branch 和 commit message 追踪状态。优点是天然分布式；缺点是 git 操作昂贵，频繁创建分支污染仓库，紧凑/变基场景不稳定。

## 理由

1. **紧凑安全** — 紧凑事件只影响当前会话上下文，而 `token.json` 在磁盘上独立存在。紧凑后读取 token 即可恢复。
2. **并发安全** — Lock 文件 + PID 验证防止两个会话同时写同一任务。锁文件通过 `flock`（原子操作） + 进程退出时内核自动释放。
3. **零外部依赖** — 纯文件系统机制，不需要数据库、Redis 或任何第三方组件。
4. **轻量高效** — Token JSON 通常 < 1KB，读取成本极低。
5. **可审计** — Token 状态链记录了任务的完整生命周期，包括失败和重试。

## 后果

- 每个任务启动时需先获取锁（阻塞或失败）
- 紧凑事件后需通过 `token.json` 恢复 outline 和 sessionId
- 需要在 `.omc/.gitignore` 中排除 lock 文件（不提交）
- 需要在进程启动/退出时清理 stale lock（警惕孤儿锁）
- 长任务需要在 token 中记录 checkpoint 以实现断点续传
