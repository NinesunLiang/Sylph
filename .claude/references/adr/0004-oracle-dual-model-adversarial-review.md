# 0004. Oracle 双模型对抗审核

**日期**: 2026-07-24
**来源**: oracle-spec.md, oracle 门禁设计

## 上下文

单一模型的代码审核存在固有的盲点问题。研究发现，语言模型在审查自己生成的代码时倾向于给出正面评价（自确认偏见），且不同模型在不同类型的缺陷上各有强弱项。当只使用一个模型进行审核时：

1. **幻觉式批准** — 模型认为代码正确但实际上有隐藏 bug
2. **风格偏见** — 模型偏好某种代码风格而非客观正确性
3. **模式统一** — 所有审核趋于一致的错误模式和遗漏方式

需要一个机制来提供独立、交叉验证的代码审核。

## 决策

实施 Oracle 双模型对抗审核体系，分为三种运行模式：

**Oracle-D（静态分析）**：
- 聚焦代码结构、模式、规范性
- 检查：架构违规、不变量违反、死代码、接口不一致
- 不执行代码，只做语法树和模式匹配级别的分析

**Oracle-V（运行时验证）**：
- 聚焦行为正确性、边界条件、错误处理
- 检查：测试结果、构建日志、运行时行为
- 需要实际执行测试或运行代码

**Duo 模式**：
- Oracle-D 和 Oracle-V 同时运行
- 结果交叉校验：两者必须都通过才算通过
- 分歧时进入仲裁流程（第三个模型做 tiebreaker 或告警由人类裁决）

每个 Oracle 使用不同模型运行（如 Oracle-D 用 Sonnet, Oracle-V 用 Opus），消除模型特定盲点。

## 替代方案

- **单一 Oracle** — 只用单个模型完成所有审核（静态+动态）。优点是成本最低；缺点是自确认偏见不可避免，单模型盲点无法补偿，高危场景下风险不可接受。
- **三模型投票** — 三个不同模型独立审核，多数通过即可。优点是更高的容错性；缺点是成本增加 50%（相对于双模型而言）[内部自检，非行业标准]，且三模型可能共享某些训练数据中的共同偏见。
- **规则引擎替代** — 使用 ESLint/Prettier 等传统工具做审核。优点是零偏见、确定性。缺点是无法理解语义、无法检测架构级别的问题、无法发现新增缺陷模式。只能补充而非替代模型审核。

## 理由

1. **自确认偏见消除** — 两个模型独立判断，不会因同一段代码的生成-审核同源而产生偏见
2. **盲点覆盖** — 不同模型家族（Sonnet vs Opus vs DeepSeek）在不同缺陷类型上各有优势，互补覆盖
3. **分工明确** — Oracle-D（静态）和 Oracle-V（动态）各自专业化，避免一个模型既要理解结构又要理解运行时行为导致的不专注
4. **仲裁机制完善** — Duo 分歧时有明确的升级路径（第三模型或人类）
5. **成本可控** — 相比三模型，双模型在成本和覆盖之间取得最佳平衡

## 后果

- 每次 Oracle 审核需要两次模型调用（Duo 模式），成本增加约 2 倍
- Duo 分歧时需引入仲裁流程，增加了延迟
- 需要为 Oracle-D 和 Oracle-V 分别配置不同的 prompt 和规则集
- 需要维护模型选择策略：哪些场景用哪对模型组合
- 审核结果需要记录两个 Oracle 的独立证据，便于分歧时的追溯
- 模型升版时需要重新校准审核标准的一致性
