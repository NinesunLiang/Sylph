# 0013. Scorecard 自评度审计门禁

**日期**: 2026-07-25
**来源**: Grill-me 设计审阅 (scorecard 9.0+ 路径)

## 上下文

Scorecard 自评（8.65）与外评（7.67）之间存在 **-0.98 的显著偏差**。根因分析确认：自评基于设计意图，外评基于运行时实测。这种偏差若持续存在，会导致：

1. **门禁形同虚设** — 加权 8.6 的门禁线实际上可能只有 7.6 的真实水平
2. **迭代方向错误** — 团队以为补了坑，实际外评并不认账
3. **信任损耗** — 每次自动审都要追问"自评可不可信"

大多数同类系统（AI Agent 治理框架）都面临这个困境，但**没有一个在 self-rating 上设自动化门禁**。

## 决策

**建立 scorecard 自评审计门禁**，规则如下：

1. **证据溯源规则** — scorecard 中每项分数提升，必须在本行或紧邻行附带可验证的 file:line 引用。不满足则自动回退到外评分数。
2. **双模型交叉校验** — 每轮 scorecard 更新触发一次 Oracle Duo（当前模型 + 对立模型）独立评分。**分差 ≥1.0 的项标黄**，需人工仲裁。
3. **组合执行** — 先过证据溯源筛（防无源断言），再过双模型验证（防有源但逻辑牵强）。

门禁执行点：`compound-verify-gate.py` PostToolUse:Write(scorecard.md) 或 PreToolUse:Edit|Write on scorecard.md。

**Phase 2 实现**: `compound-verify-gate.py` 完成双模型交叉校验，对比两个模型评分，
Δ≥1.5 的维度自动标注 `⚠️ 仲裁中`。

## 替代方案

| 方案 | 做法 | 放弃理由 |
|------|------|---------|
| **纯证据门禁**（轻量） | 只检查 file:line 引用，不过双模型 | 无法防御「有引用但逻辑不对」的虚假提分 |
| **纯双模型校验**（中量） | 每次提分跑 Oracle 交叉验，不要证据 | 冷启动时双模型也无基线数据可参考 |
| **提交后外评报告**（审计型） | 不提分门禁，更新后自动跑外评给偏差报告 | 不能阻止虚高写入 scorecard，信任建立慢 |
| **基线冻结** | 锁定当前分数，只降不升直到外评确认 | 太极端，阻碍真实改进的确认速度 |

选中的「组合型」是以上权衡后的最优解：门禁前置 + 事后验证双保险。

## 理由

1. **断崖感** — 业界没有同类系统在 self-rating 上设自动化可审计门禁。突破「自评虚高」本身就是品牌信任的建立
2. **成本可接受** — Oracle 校验不是每次工具调用都跑，只在 scorecard 写入时触发（低频高价值）
3. **门禁型 > 审计型** — 防的投入比追的投入小一个数量级。scorecard 一旦写入历史就很难撤回
4. **冷启动有兜底** — C6/E5/学习笔记等积累型维度在冷启动时使用「下限保护」而非「门禁拒绝」

## 后果

1. **scorecard 维护成本上升** — 每次提分必须附证据（这是预期内的，也是提分本身该做的事）
2. **可能需要调整 ADR-0003 VerifyGate 证据等级** — 基础证据格式要复用
3. **双模型校验的 token 开销** — 每轮 scorecard 更新约 2-5 次 Oracle 调用
4. **自评 vs 外评的 Δ 会自然收敛** — 这是预期收益
