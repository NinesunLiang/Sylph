# 0005. Goal 模式自主执行 + skip-risk 安全阀

**日期**: 2026-07-24
**来源**: RPE 开发流程, 任务架构设计

## 上下文

AI 需要能够在无人值守的场景下自主执行多步骤任务。但完全自主的执行能力伴随着风险：

1. **危险操作** — 删除文件、修改关键配置、执行破坏性命令
2. **不可逆操作** — 强制推送、覆盖分支、清理数据
3. **循环浪费** — AI 陷入错误循环导致 API 成本飙升

需要一套机制来平衡自主执行效率和安全性。

## 决策

实施三层安全架构（L1/L2/L3）配合 7 步执行流程 + 退出验证：

### 三层安全边界

| 等级 | 行为 | 处理 |
|------|------|------|
| **L1 硬边界** | `rm -rf`、`git push --force`、`DROP TABLE` 等 | 永不执行，直接拒绝 |
| **L2 skip-risk** | `git push` 到 shared branch、批量删除文件 | 跳过 + 记录到 skip log |
| **L3 blocked-human** | 影响外部服务的操作、涉及真实数据的变更 | 暂停并等待人类审批 |

### 7 步执行流程

1. 接收目标
2. 制定执行计划并请求确认（消除误解）
3. 执行计划（每步检查 L1/L2/L3 边界）
4. 自动验证（E2+ 证据）
5. 记录执行日志（含所有 skip-risk 条目）
6. 生成退出报告（汇总结果 + 所有跳过的风险操作）
7. 发送通知（仅失败/阻塞时）

### skip-risk 安全阀

L2 跳过不阻断流程，但必须在退出报告中自动聚合展示："以下 N 个操作因风险跳过，请人工审查"。这使得流程不会被阻断在非关键操作上，同时保持审计完整性。

## 替代方案

- **完全自主** — 不设任何安全边界，AI 可以执行任何操作。优点是执行效率最高；缺点是灾难级风险，一次误操作即可导致数据丢失或仓库破坏，在任何团队中都不被接受。
- **每步审批** — 每个操作都需要人类批准。优点是安全性最高；缺点是完全违背"自主执行"的初衷，人类必须全程值守，实际退化为半自动工具。
- **白名单模式** — 只允许执行预定义白名单中的命令。优点是策略明确；缺点是过于僵化，无法覆盖所有合理操作，需要频繁维护白名单。
- **沙箱执行** — 在 Docker/Sandbox 中执行所有操作，完成后同步结果。优点是隔离性好；缺点是 Docker 依赖增加环境复杂度，CI 流水线中配置困难，无法操作本地文件系统。

## 理由

1. **分级安全** — L1/L2/L3 覆盖不同风险等级，不搞一刀切
2. **流程不断** — skip-risk 跳过但不卡住，关键路径不被非关键阻挡
3. **审计闭环** — skip log + exit report 确保所有跳过操作都有记录
4. **7 步完整** — 从目标确认到退出验证形成闭环，减少遗漏
5. **通知仅异常** — 不产生噪音，人类只在真正需要时才被介入

## 后果

- 需要维护 L1/L2/L3 的操作清单（可扩展，随项目演进更新）
- skip-risk 条目可能被滥用（AI 将高风险操作标记为 skip-risk 来绕过审查），需要 audit 机制
- 退出报告需要人工审查 L2 条目，增加了 review 负担
- 7 步执行流程增加了固定开销（即使简单任务也要走完整流程）
- L3 blocked-human 场景需要设计通知通道和响应超时策略
- 需要先针对非关键任务充分测试三层安全边界的准确性
