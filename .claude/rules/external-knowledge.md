# External Knowledge Rules（项目外知识获取优先级）

适用范围：AI 需要**项目之外**的知识、方案、库或实现时
目标：不要闭门造车，不要把「自己实现」当第一选项

## Rule 1：三级优先，顺序不可颠倒

遇到项目外的问题，按这个顺序找答案：

```
0. 项目内现有方案 ── 仓库里已有的实现 / 脚本 / 工具 / 配置 / 既有模块
1. 官方优先 ── 官方文档 / 官方仓库 / 官方规范 / 官方公告
2. 社区大牛 ── 公认的社区权威实践、维护良好的开源项目、被广泛引用的方案
3. 自己实现 ── 以上都找不到，才自己写
```

> 2026-10-18 人类裁决：**项目内现有方案优先于官方**。
> 先找仓库里有没有现成的，避免在已有轮子旁边再造一个劣化版。

**不许跳级。** 直接跳到第 3 级是最常见的错误 —— 常常造出一个已有轮子的劣化版。

## Rule 2：每一级的判定标准

| 级别 | 算数的来源 | 不算数的来源 |
|---|---|---|
| 项目内现有方案 | 本仓库既有代码 / 脚本 / 配置，且确实解决同一问题 | 名字相似但语义不同、已废弃或已删除的实现 |
| 官方 | 厂商官方文档站、官方 GitHub 仓库、RFC/规范原文、官方 issue 回复 | 二手博客转述、AI 生成的教程、SEO 农场 |
| 社区大牛 | 被广泛 star/引用且仍在维护的项目、公认专家署名且可核对的文章 | 匿名贴、无出处的「最佳实践」、日期不明的转载 |
| 自己实现 | 前两级都确认为「不存在」后的自研 | 懒得查、查不到就写、觉得自己的更好 |

## Rule 3：自研必须留证

走第 3 级时，交付里必须能看出**前两级查过**：

```text
- 查过仓库内哪些现有实现，为什么不复用（不存在 / 不适用 / 不满足要求）
- 查过哪些官方来源，结论是什么（不存在 / 不适用 / 不满足要求）
- 查过哪些社区方案，为什么不用（不维护 / 不匹配 / 有坑）
- 自研方案相对已有方案强在哪
```

优先级：项目内现有方案 > 官方 > 社区 > 自研；没有这段说明的自研，视为跳级。

## Rule 4：找到了也要核对适用性

官方/社区方案存在 ≠ 一定适用。必须核对：

- 版本是否匹配（对照官方 changelog，禁止凭先验知识假设版本）
- 许可证是否可用
- 维护状态是否活着
- 是否解决的是同一个问题

## Rule 5：引用要留痕

用了官方或社区方案，交付里要写清来源（链接 + 版本），便于日后复核。
